# Outbox relay

## Assumptions

- Tequity's endpoint runs on the grading machine itself at localhost:9000, and their load generator posts to localhost:8080 on that same machine. Our API and worker run with host networking (`network_mode: host`), so localhost inside our containers is the machine's own localhost, whatever address their endpoint listens on.
- Port 54329 on the grading machine is free. Postgres runs with host networking on that port, listening on 127.0.0.1 only, so it cannot clash with a Postgres already using the default port 5432 and cannot be reached from other machines.
- Our test rig (a fake endpoint on 9000, a load generator and a checker) runs as containers with host networking, never as programs on the developer's machine. On Docker Desktop for Windows, host-network containers and Windows cannot reach each other on localhost, while containers inside Docker Desktop's Linux VM can, the same way they do on a Linux machine.
- The relay and its test rig are written in Go. Postgres is version 16, with the image tag pinned.
- One worker process sends for every user, up to 200 users at a time. An event's `delivered_at` is the only record of progress: anything without it gets sent. After a 2xx, a failed database write of `delivered_at` is retried until it commits, and never causes a resend. The worker uses at most 20 database connections and the API at most 30, well under Postgres's 100.
- When healthy, Tequity's endpoint answers in about 10 ms or less, with 500s on at most a few percent of requests. Taking the heaviest user as 30 of the 100 events a second, that is the speed it needs to clear the backlog of a 5-minute outage within 5 minutes of recovery, counting our own 5 ms per event and the waits before retries. If the endpoint rate limits us below 200 events a second during recovery, no design meets that.
- A user's events wait while that user's oldest unsent event, by created_at, arrived less than 1 second ago. Arrival time is `received_at`, set by Postgres's clock on insert; created_at is the load generator's clock and only decides order. A later event never goes out while an earlier one is still inside its hold. An earlier event that arrives after a later one was already sent still goes out, late, and is logged.
- created_at has at most 6 decimal places of seconds. It is parsed as RFC 3339 in Go, taken as UTC when it has no time zone, cut to microseconds (logged when digits are dropped) and stored as a Postgres timestamp. Two events of one user that tie are sent in arrival order.
- "The same body" in the brief means the same bytes. Each body is stored as raw bytes and sent unchanged, with `Content-Type: application/json`.
- Two posts with the same event_id are one event. event_id is the primary key and the insert skips duplicates, so both posts get a 200 and only one row exists.
- If an event_id arrives again with a different body, the first body stands. The repeat gets a 200 and is logged.
- Intake answers 200 only after Postgres has committed the event. It answers 400 when the body is not a JSON object, or when event_id, user_id or created_at is missing, empty or unreadable, and 413 when the body is over 1 MB. `type` and `data` pass through unchecked.
- Any 2xx from the endpoint means saved. Any other status, a refused connection or a failed connect means not saved, and the event is retried after 20 ms, doubling on each failure in a row up to 5 seconds. Redirects are not followed.
- A slow answer is always waited for, and an endpoint that never answers is outside the brief's table. Sends have no overall timeout, only a 2-second connect timeout; a send in flight over 60 seconds is logged as a warning with its event_id. TCP keepalive (the system checking an idle connection's other end is still there) makes a connection whose other end has vanished fail. That failure, like any connection lost after the request went out and before a status line came back, means the outcome is unknown, and the event is sent again. The status line alone decides: a 200 means saved even if the rest of the answer is cut off.
- On a normal stop the worker starts no new sends and waits up to 120 seconds for the ones in progress, exiting as soon as they finish. The stop signal never cancels a send in progress or its `delivered_at` write. A send still going after that, or one cut short by a hard kill, is sent again on restart and may be saved twice.
- A 429 means the whole endpoint is rate limiting. All new sends pause for its Retry-After seconds, and for at least 1 second, which also covers a missing header, a value that is not a whole number and `Retry-After: 0`. A 429 does not raise the retry wait.
- Tequity starts sending once `docker compose up` shows our services running. Posts in the first few seconds may be refused, and a refused post carries no 2xx promise. Postgres keeps its data in a named volume, so stored events survive `docker compose down` and `up`. Only `down -v` deletes them, and a schema change needs it, since the init SQL runs only on an empty data folder.

## What this is

Tequity's take-home. An intake API on port 8080 stores each event in Postgres before it answers, and a worker passes the stored events on to Tequity's endpoint on port 9000, once each and in `created_at` order per user. docs/problem.md states the problem in full, and docs/decisions.md gives the reason for every choice.
