  1. Container to Windows host localhost:9000: Yes, per the docs. "This feature
  works in both directions. This means you can access a server that is running
  in a container from your host and you can access servers running on your host
  from any container that is started with host networking enabled." The docs'

  server on the host's port 80. The page does not say anything Windows-specific
  about this.

  2. Host to host-mode container port via localhost: Yes. The docs' example runs
  `nc -lkv 0.0.0.0 8000` in a `--net=host` container, then says "Port 8000 will
  then be available on the host" and connects with `nc localhost 8000`. TCP and
  UDP are both listed as supported.

  3. Requirements:
  - Docker Desktop 4.34 or later. The page says "Host networking is supported on
  Docker Desktop version 4.34 and later."
  - Sign in to your Docker account in Docker Desktop.
  - Settings > Resources > Network, check "Enable host networking", then "Apply
  and restart".
  - Subscription: the page does not mention any subscription or paid-plan
  requirement.

  4. Limitations (from the Docker Desktop "Limitations" list):
  - Processes inside the container cannot bind to the host's IP addresses,
  because the container has no direct access to the host's interfaces.
  - Works at layer 4: "network protocols that operate below TCP or UDP are not
  supported."
  - "This feature doesn't work with Enhanced Container Isolation enabled."
  - "Only Linux containers are supported. Host networking does not work with
  Windows containers."
  Also, the general host-mode note: `-p`/`--publish`/`-P`/`--publish-all` are
  ignored with the warning "Published ports are discarded when using host
  network mode".

  5. Linux Docker Engine caveats:
  - The container shares the host's network namespace, is "not isolated from the
  Docker host", and gets no IP address of its own.
  - Port mappings are ignored (see the warning above).
  - Performance benefit: no NAT and no "userland-proxy" per port.
  - Port 80 example requires that port to be free on the host.
  - The Linux prerequisites section says "The host networking driver only works
  on Linux hosts, and as an opt-in feature in Docker Desktop version 4.34 and
  later." This sits oddly with the Docker Desktop support stated elsewhere on
  the page. Treat the page's Desktop support as stated, but note the
  inconsistency.
  - Swarm services: with `--network host`, a service container binding port 80
  means "only one service container can run on a given swarm node."

● The problem

  - Tequity's brief puts their endpoint at localhost:9000 on the grading machine
    (plain Docker on Linux).
  - Inside a container, localhost means that container. Our workers need some
    other route to the machine's own port 9000.
  - Their load generator also posts to localhost:8080 on the machine, so our
    intake API has to be reachable there.
  - The brief doesn't say which network address their endpoint listens on. That
    turns out to matter most.
    - Some servers accept connections only from the same machine (they bind to
      127.0.0.1).
    - Others accept from anywhere.
    - Python web servers such as Flask and uvicorn default to the first kind.

  Option A: host networking for the API and workers

  - How: set network_mode: host on those services in compose. The containers
    then share the machine's network.
    - localhost:9000 inside the container is the machine's own port 9000.
    - Our API listens straight on the machine's port 8080.
  - On Linux:
    - It reaches their endpoint whatever address it listens on.
    - The machine's firewall has no say, because the traffic never leaves the
      machine's own network.
    - The URL in our code is exactly the brief's: http://localhost:9000/events.
  - On Windows: Docker Desktop has supported this since version 4.34, but only
    once it's switched on.
    - Sign in to Docker Desktop.
    - Go to Settings, then Resources, then Network, and tick "Enable host
      networking".
    - Enhanced Container Isolation (a Docker Desktop security mode) has to stay
      off.
    - Docker's docs say it works both ways: the container reaches the machine's
      localhost, and the machine reaches the container's ports.
  - Costs:
    - Our ports take the machine's ports directly. If anything else on their box
      already uses 8080, we fail to start. The brief needs 8080 from us either
      way, so that risk exists in every option.
    - Containers on host networking can't find other services by name. Postgres
      becomes a localhost address too, which raises a port question I'd settle
      next.
    - On your laptop it fails until the setting is on. You fix that once, by
      hand.

  Option B: the normal compose network plus a name for the host

  - How:
    - Add extra_hosts: ["host.docker.internal:host-gateway"] to the workers.
      That gives the host machine the name host.docker.internal inside the
      container.
    - Post to http://host.docker.internal:9000/events.
    - Publish port 8080 the normal way.
  - On Windows: it works with no setting changes, since Docker Desktop provides
    that name already.
  - On Linux: it needs Docker Engine 20.10 or later, which is from 2020.
  - Costs:
    - It fails if their endpoint accepts connections only from the same machine.
      Traffic from the container comes from the Docker network, so it would be
      refused.
    - It can fail if their machine runs a firewall. Ubuntu's ufw, for example,
      drops traffic from Docker networks to the host by default.
    - We can't see or fix either of these on their box.

  Options I dropped

  - Hard-coding Docker's host address (172.17.0.1).
    - It has Option B's risks.
    - It's also wrong on Docker Desktop.
  - A setting that switches between A and B.
    - The graders edit nothing, so the default must already be right for Linux.
      The switch would only help us.
    - CLAUDE.md's "Small" rule argues against adding config.
  - A forwarding container on host networking.
    - Our workers would still need to reach it across the Docker network.
    - So Option B's problems come back.

  My pick: Option A

  - Where each option breaks decides it.
    - A can only break on your laptop, and turning one setting on fixes it.
    - B breaks on their grading box, through an endpoint address or firewall we
      can't see. If that happens, nothing gets delivered.
  - A also matches the brief exactly: our code uses the same localhost address
    the brief gives.
